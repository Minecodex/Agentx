# 应用批量调用设计

状态：`implemented`。本文描述 plan10 的实现约束；接口与 Schema 以同步生成的契约为准。系统验收和临时资源清理已完成，实际结果及保留的原始失败见 [实施记录](evidence/implementation.md)。

## 1 系统路径与职责

```text
设计态
应用详情 / 访问界面
  → 既有设计态 Host / Agent Core / 平台 AI 模型
  → 当前工作 HTML / 隔离模拟 / 检查 / 用户明确发布

运行态
AI 生成页面 → 可信宿主 / 受限 SDK ─┐
正式应用 API ────────────────────┤
  → Runtime Gateway 认证、发布校验与批次受理
  → Runtime MySQL 批次 / 输入 / Outbox
  → 批次协调 → 原正式 Invocation 受理服务
  → 既有 Coordinator / Worker / 等待 / 审批 / Artifact

管理态
应用详情 / 调用记录 / 批次记录
  → Control BFF 对象权限 → Runtime 授权查询
  → 单项链接：原执行记录 / 待审批
```

批次协调属于现有 Workflow Runtime 构建产物，不新增常驻服务或通用调度平台。节点执行、Provider 调用、工具审批、费用和错误继续由原运行链处理。Control 不直接访问 Runtime 数据库、Redis 或对象存储；Runtime 不回读 Control 来获得业务版本。

导入解析、预览和 AI 创作不创建批次或业务 Invocation。正式批次只由获准用户明确提交或服务调用者通过正式 API 创建；设计态 Agent 没有真实提交、授权、审批或发布能力。

## 2 业务对象与权威数据

| 对象 | 所属域 | 必要内容 |
| --- | --- | --- |
| Application Batch | Runtime | 租户、应用、真实主体、来源、名称、实际 Bundle、输入契约指纹、页面发布绑定、受理时间、派发状态、操作修订 |
| Batch Item | Runtime | 稳定 itemId、clientItemId、原始序号、完整输入快照、输入 Hash、派发状态、Invocation 关联、来源批次/项目关系 |
| Invocation / TaskView | Runtime | 原业务状态、执行、等待、审批、输出、费用和文件；仍是单项权威 |
| Batch Export | Runtime Artifact | 批次和查询快照、字段/状态范围、归属、文件引用、Hash 与保留关系 |
| 页面草稿与发布物 | Control / Runtime 发布副本 | 仍按 plan9 保存和激活，冻结新增批次契约与 SDK |

新增 `application_batches` 与 `application_batch_items` 两张 Runtime 表，并复用现有幂等、命令、Outbox 和 Artifact 机制。导出采用 `export_batch` 命令与普通 CSV Artifact，不新增导出任务表，也不创建伪 Invocation。

项目保存完整输入，而不是只保存浏览器待提交队列。原始导入文件可作为来源 Artifact 引用，但不能在恢复时重新解析最新文件来替代已受理输入。每个项目至多关联一个原始业务 Invocation；重做创建新的派生批次，不覆盖该关联。

必要约束包括 `(tenant_id,batch_id,client_item_id)` 与 `(tenant_id,batch_id,ordinal)` 唯一性，以及项目与 Invocation 的租户/应用归属。clientItemId 表示本次明确提交的一行，不能以内容 Hash 去重两条相同输入。

## 3 接受整个批次

1. 验证当前主体、应用调用权、受支持发布、页面修订或 API 版本选择，以及批次大小和请求体限额。
2. 完成公共参数合并后，逐项按同一冻结输入 Schema 校验完整值、附件引用和必需身份信息。
3. 同一事务保存批次、所有项目、输入/文件/Bundle 引用和派发 Outbox；提交成功才返回受理结果。
4. 后台协调逐项调用原正式受理服务。受理请求断线、浏览器退出或后续发布切换不撤销该持久批次。

接受前有任一错误则整批拒绝，不创建部分任务。错误返回批次字段与 `items[i].input` 对应的精确 JSON Pointer、clientItemId 和导入行号；前端校验只改善体验，不能替代服务端判断。

首版上限为每批 1–100 项、结构化创建请求不超过 1 MiB、项目/批次列表每页 1–50 条。初始每批同时推进最多 4 个非人工等待项目，租户及资源准入始终优先；不新增用户可随意放大的并发配置面板。P10-00 验证这些上限与现有 Bridge、数据库和队列限制一致，不将其作为生产容量认证结论。

## 4 幂等与派发恢复

创建批次和改变批次状态使用稳定业务幂等键；范围为租户、应用、真实主体、操作与请求键。网络重试返回原结果，同键不同规范化输入 Hash 返回冲突。JSON-RPC ID、模型工具 ID、数组位置和输入内容 Hash 均不能替代业务请求键。

项目派发使用 Batch Item ID 对应的固定受理意图，不能在重启后生成随机新请求键。复用同一 Runtime 数据库事务，将 Invocation 的正式受理与项目关联一起提交。内部 `create_batch_runtime_invocation_tx` 使用 `batch:{itemId}` 作为受理键，只接受可信持久行和冻结 Bundle；公开接口不能指定任意历史业务包。不另建异步补关联路径。

协调器使用既有 MySQL Outbox、Lease/Fencing 和 Recovery。Redis 仅负责可重建的派发，不保存唯一的剩余项目列表。重复派发、两个协调副本竞争、租约过期、受理后写关联前强退，都必须收敛到同一项目和同一原调用。

429、队列水位和瞬态依赖不可用会使未受理项目保持待派发，按现有重试时限与退避恢复，不写成业务失败或创建假调用。确定性的撤权、版本不可用或输入绑定拒绝记录为项目受理失败，保留阶段和错误；界面不得给它虚构 Execution ID。

批次公平推进，人工等待不占 Worker 线程或该批活跃执行槽。租户总在途限制仍包含其正式定义中的等待调用；资源压力时允许继续排队，不能借批次绕过全局背压。

## 5 状态与进度

批次持久化自身的派发控制状态 `active/stopped/finished`、停止修订和协调租约。`finished` 只表示所有项目已完成派发处置，不表示所有业务调用已结束；`stopped` 保留明确停止事实。项目持久化待派发、已受理、受理失败或未开始即取消的事实；业务状态从关联 Invocation/TaskView 读取，不复制一个独立的业务状态机。

BatchView 返回总数、排队、执行、待输入、待审批、成功、失败、取消、结果待核实和已结束计数，以及快照修订。未开始项目的终止和受理失败须明确来源阶段。已结束计数包含成功、确定失败和取消，不把结果待核实算作已成功或已结清。

界面状态由计数和派发控制事实确定：有可运行工作显示处理中；仅剩资料/审批显示待处理；存在未知副作用显示待核实；全部结清后区分全成功、部分失败和取消。一次失败不默认取消其他独立项目。

批次只读查询及导出快照冻结使用事务级 `REPEATABLE READ` 与一致性快照聚合；原 Runtime 写入连接仍为 `READ COMMITTED`，不修改池的会话默认值。分页游标绑定租户、应用、主体、过滤条件和顺序。Trace/ClickHouse 延迟不能改变业务状态。金额只按应用实际声明的字段和币种汇总，不猜字段名，不混算不同币种。

## 6 停止 取消与失败重做

| 操作 | 语义 |
| --- | --- |
| 停止后续派发 | 原子记录停止修订，使尚未受理项目进入未开始即取消；已受理项目继续 |
| 取消未结束项 | 先停止派发，再向每个符合取消条件的原 Invocation 发出既有取消命令；受理和实际结束分别展示 |
| 单项补充资料 | 按原 taskId、waitId、修订与 responseSchema 恢复，不新增调用 |
| 人工审批 | 在既有审批中心处理原审批对象；批次和生成页均不产生批准能力 |
| 失败项重新执行 | 明确确认后，为符合条件的项目创建一个新派生批次；原批次和调用保持不变 |

停止与受理以同一批次修订和项目条件更新串行化。停止提交之前已完成受理的项目属于已开始项；仅取得旧派发租约但尚未受理的项目不能在停止后继续创建新调用。

重做是新的业务意图，使用当前有效发布、当前权限与独立请求键，记录 `sourceBatchId/sourceItemId/sourceInvocationId`。原输入契约和当前契约不同则拒绝自动复制执行，转为普通新建批次的显式修正与重新校验；不猜改名或转换字段。

服务端根据原调用结果与现有 Effect/Receipt 证据返回允许动作。结果待核实禁止直接重做；已确认发生不可重放副作用的失败不提供整项重做，继续使用原有核实/恢复路径。可重做项必须再次执行当次业务审批，不复用旧批准。平台幂等只能保证受理和关联收敛，不能声称任意外部系统实现了 exactly-once。

## 7 身份与授权

- 员工查询仅返回当前应用、当前可信主体的批次及其单项。batchId、itemId、taskId 和 URL 参数都不是凭据。
- 应用 API Key 保持原服务主体作用域与撤销规则，不借用员工身份。客户端输入的 userId、clientItemId、申请人姓名或 `apiUserIdInput` 不构成认证。
- 管理查询继续检查应用对象范围和已有执行查询权限；不能因能看批次统计就自动获得输入正文、内部 Trace、审批材料或所有文件。
- 管理操作复用已有应用/执行操作权限并做对象复查；若没有足够的既有权限，P10-00 在同一 IAM 模型补充最小操作权限，不增加独立 Batch ACL 系统。
- 每项开始前复查当前应用 Admission、工作流运行身份和资源状态。冻结版本不冻结未来使用授权；撤权后不再创建获准的新业务调用。
- 网页和 API 的创建、分页、单项读取、补充、取消、重做和导出执行相同主体及对象边界。服务主体不能提交预设 `waitInputs`，沿用既有 external 等待语义。

单项调用采用无 Session 的完整参数入口；不把同一批次的多行放进一个共享会话。长期记忆继续按既有应用和可信来源用户作用域读写，不自动增加 batch/item 记忆身份。依赖跨行累计状态或顺序的业务应在工作流中明确处理，不宣称为相互独立的批次项目。

## 8 发布绑定与历史恢复

批次受理时冻结应用、实际 Deployment/Bundle、工作流版本、输入契约 Hash、来源及可用的页面 Publication/SDK/样式。网页创建带预期发布修订，发布竞争返回冲突并保留用户未提交数据，不静默改用新业务版本。

已受理的未派发项目属于原批次后续工作，可使用冻结业务包继续受理；不能重新经过「当前页面新提交」入口而误拒绝旧版本，也不能伪造新的历史页提交。此路径仍受当前授权和停用规则约束。

实施中的并发决策：`application_batch_items.active_slot` 持久保存项目许可，初次派发和既有 Runtime 的节点调度、工具审批恢复共用批次行锁。只限制初次派发不能防止多个已等待项目同时恢复后超过 4 项，因此恢复也必须先取得原项目许可；没有许可时保留原命令，项目显示排队。后台协调在取得批次锁后的同一快照中确认整个原 Execution 树没有排队/执行中的 Attempt，才为人工等待或结束项目释放许可。部分分支等待、其他分支仍执行时不释放。此调整仍使用现有两张批次表、命令和恢复循环，不增加服务或执行引擎。

批次同时冻结受理时的身份映射策略和逐项身份，包括“无 API 用户”的空值。派发时不从新发布的映射推导身份，当前主体授权与停用状态仍逐项重新检查。行标识和业务幂等键采用二进制、区分大小写的排序规则。

API 批次独立保存受理当时可用的 `history_page_id`，只选择与冻结业务包完全相同且已启用的页面；没有匹配页就保持空值，通过 API 处理记录。它不作为网页调用入口的授权绑定，也不随日后页面发布而补填。网页批次保存其明确提交的 Publication。批次明细公开 `pagePublicationId` 供可信宿主核对，历史打开始终取这个固定对象。

新增 `openBatch(batchId)` 由可信宿主读取获准来源，加载该批次原页面，并将 batchId 注入上下文。原页面不再是当前发布时进入历史模式，只查询、补充或取消原项目；禁止创建旧版本的新批次。当前页面列出旧批次摘要后，必须通过 openBatch 打开，不在当前契约下强行渲染旧正文。

历史页显式选中安全失败项重做时，请求仍针对原批次，服务端重新授权并创建绑定当前发布的派生批次，可信宿主随即打开新批次自己的页面。原页面不能指定旧包创建新批次。创建与派生重做的待确认意图都由宿主保存原业务键和输入摘要，断线后的新通信请求重放原意图。

网页派生重做在受理事务内核对当前页面绑定包与当前业务 Head，二者不一致时返回 409，要求先发布当前业务版本的页面，不落入旧包。当前页面绑定的包已停用或不存在时，普通创建返回对象不可用，不将零行查询误报为数据库故障。

API 创建的批次不假设存在网页发布；仅在存在精确匹配 Bundle 的可访问发布页时提供链接，否则继续使用正式 API。页面物料或 Hash 无效时明确失败，不临时生成或换用最新页面。

## 9 API 与受限 SDK

以下为当前 Gateway 路由；OpenAPI、Rust DTO、JSON Schema 和 TypeScript 由协议生成，保持一致。

| Gateway 能力 | 路径 | 返回或作用 |
| --- | --- | --- |
| 创建/列出本人批次 | `/gateway/v1/applications/{slug}/batches` | POST 返回受理 BatchView；GET 返回有界分页摘要 |
| 页面绑定创建 | `/gateway/v1/pages/{slug}/batches` | 核对当前页面发布 ID 和修订后受理，不能指定任意历史包 |
| 查询批次/项目 | `/gateway/v1/batches/{id}`、`/{id}/items` | BatchView 和分页项目视图 |
| 停止/取消 | `/gateway/v1/batches/{id}/stop`、`/{id}/cancel` | 持久操作受理与当前修订 |
| 重做失败项 | `/gateway/v1/batches/{id}/rerun` | 新派生 batchId，不覆盖原项目 |
| 汇总导出 | `/gateway/v1/batches/{id}/exports` | 冻结快照的导出任务/Artifact |
| 解析导入文件 | `/gateway/v1/applications/{slug}/batch-imports/parse` | 授权 Artifact 的表头、单元格和定位信息，无业务调用 |

Control 增加当前应用的批次管理 BFF 和批次归属过滤，访问 Runtime 的正式内部服务，不复用员工接口去伪造他人主体。确切管理/内部路由、权限和审计事件在 D10-03 冻结。

页面 SDK 增加 `createBatch`、`listMyBatches`、`getBatch`、`listBatchItems`、`openBatch`、`stopBatch`、`cancelBatch`、`rerunFailedItems`、`exportBatch` 和 `readTable` 等受限能力；它们只能操作宿主绑定的应用。批次刷新先采用有界轮询和分页，不为每行打开订阅；原单项详情继续复用现有 getTask/subscribeTask。

`getContext` 增加可用批次能力及 batchId；原 taskId 与 batchId 的初始页面目标互斥。每个 Batch Item 返回获准 Task 摘要和现有允许动作，补充、审批跳转与单项文件下载复用现有 SDK。批次导出文件使用独立获准引用，不能虚构一个 taskId 去调用原单项下载接口。

HTML 不传应用 ID、任意 Endpoint、可信主体、管理员 Token 或无限并发参数。SDK/Bridge 保持严格 Schema、大小/并发/超时、稳定请求键、会话失效和历史模式检查；批次能力不变成通用 fetch 或代码执行入口。

## 10 导入 导出与文件

仓库已有 Rust `csv` 依赖，前端没有直接声明的 CSV/XLSX 解析包。首期 CSV/TSV 解析优先复用 Rust `csv`：可信宿主上传受支持文件，Runtime 验证归属后解析返回有界表格数据，AI 页面做显式列映射和编辑。粘贴表格经同一解析规则处理，不在每份生成 HTML 中手写分隔符算法。

原生 XLSX 不在本期。解析接口不执行单元格公式、不加载远程链接，不按用户提供的 URL 或本机路径取文件。导入文件大小、返回大小和最多 100 行在解析前后分别检查；结构化字段只接受显式完整值，不靠模型猜数据。非法扩展名、编码、引号或超限返回定位信息。

附件输入仍使用应用冻结 Schema 和既有 uploadFile。批次受理时为未派发项目的附件建立 Retention 引用，项目受理后交接给 Invocation；失败、取消、重做与导出都要回收或保留正确的引用。共享文件逐项检查，不能借批次扩大文件归属。

未受理的取消/失败项目继续持有输入引用，直到批次本身过期清理。管理员对已获对象查看和运行授权的来源行派生重做时，内部受理路径验证来源批次、行和完整输入 Hash，并检查原主体对附件的所有权，才为新主体创建项目输入引用；新 Invocation 仍使用管理员自己的当前身份和权限。公开创建不能声明来源或任意授予附件权限。

Runtime S3 客户端启用标准 ETag 条件写；导出使用 `PutMode::Create`，崩溃后已存在文件必须读取并核对 Hash，不能覆盖原快照。

CSV 导出基于服务器冻结的批次/项目快照，包含固定行标识、原始序号、状态、实际输出/错误及来源，不把失败或未知写成成功。字段来自实际输出契约，金额按币种分开；正文、文件引用和字段脱敏遵守管理/本人/服务权限。使用成熟 CSV 写入器，并对公式触发文本做导出转义，不修改权威业务数据。

## 11 AI 创作与预览检查

复用原平台模型、Host/Core、工具 Registry、页面草稿、修订、自动保存和用户发布。创作上下文提供真实单项输入输出、文件与等待契约、批次 SDK/BatchView/允许动作，以及单次调用与批次调用的区别；不让 AI 自行创建 Batch 后端或修改工作流。

新增标记和检查契约必须覆盖表格字段、稳定行标识、批次提交、分页明细、历史打开和导出，沿用既有可访问标签。单项提交仍要求一次动作对应一个任务；批量提交要求一次动作对应一个批次和恰好 N 个有效项目，不允许循环 invoke、空白行、漏行或重复提交。

模拟器构造完整批次、跨版本历史以及包含多个并行待办的 TaskView，异步推进状态。页面必须查询后续状态；后台更新不得清空正在填写的输入或已选行。复制、导入、校验、筛选和预览都不得创建正式业务调用。真实测试及发布继续由可信 UI 明确发起。
