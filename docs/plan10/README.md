# plan10 应用批量调用与 AI 页面创作

状态：`complete`。更新日期：2026-11-03。P10-00 至 P10-06 已完成，31 项适用系统门禁、三类真实 AI 页面及 6 批次/18 项正式业务通过；中英文和明暗桌面、完整历史、原 API/MCP/会话回归通过。该轮验收的临时资源和测试凭据已清理，常驻环境当时保持原版本。结果见 [实施记录](evidence/implementation.md)。随后按用户要求完成常驻升级；[本地批量报销体验](evidence/2026-11-03-local-demo.md)的六项部署/接口检查通过，已保留四个真实 API 批次和页面草稿，员工页面发布与浏览器检查仍待完成。原始 Demo 仅用于解释功能位置。

本计划让管理员继续通过应用详情的「访问界面」描述批量业务需求，由现有 AI 页面创作生成清单录入、逐项处理和结果展示。平台提供持久批次、后台派发、权限、恢复和导出；每个业务项目仍通过原有 Application Invocation 和 Workflow Runtime 执行。

## 1 产品入口

沿用当前 Agentx 企业工作台、侧栏、紫色主题、共享组件和应用详情页签，功能放在以下三个位置。

| 位置 | 用户操作 | 变化 |
| --- | --- | --- |
| 应用 → 应用详情 → 访问界面 | 在原有右侧 AI 页面创作中输入批量需求，左侧预览，再用原发布按钮发布 | 扩展创作上下文、受限页面 SDK 和模拟检查，不新增页面独立创作入口或模型设置 |
| 应用 → 应用详情 → 调用记录 | 在「单次调用」「批次记录」间切换，查看批次和逐项结果 | 增加批次记录子页、批次详情及原调用关联 |
| 应用列表或访问界面 → 打开应用 | 员工在原 `/a/{slug}` 页面选择单条或批量办理 | 同一应用、同一访问地址；具体业务布局由 AI 生成 |

批次详情中的单项链接进入既有执行记录；审批进入既有「待审批」。员工页面只展示获准待办并提供受控跳转，不获得审批决定权、管理权限或 Trace 权限。不增加全局批处理中心、通用 OA 或第二套任务工作台。

1. 「页面创作」：现有应用详情和 AI 创作面板，单条与批量报销共存。

Demo 中来源收敛为「业务网页」「应用 API」，与本计划首期范围一致。已有「MCP 接入」页签保留原功能；新增 MCP 批次工具不在本计划内。

## 3 批量业务的定义

| 情形 | 处理方式 |
| --- | --- |
| 多个产品组成同一张报价单，或多个明细组成同一业务单 | 原工作流声明数组输入，页面提交一次 Invocation；需要逐项逻辑时使用既有 Loop |
| 多个客户分别生成报价，或多张报销单分别办理 | 创建一个 Batch，每行是一次独立 Invocation，具有自己的输入、待办、结果和费用 |
| 业务需要跨行顺序依赖、共享对话或最终整体审批 | 在 Workflow 中明确编排，不由生成页面或批次协调隐式推导 |

Batch 是调用集合与派发控制对象。Invocation 仍是单项业务任务的权威对象，`taskId` 仍等于 Invocation ID；Batch 不增加另一套工作流引擎或 Agent loop。

## 4 首期交付范围

- 参数调用型应用的网页和正式应用 API 批量入口；每行提交完整、符合已发布 Schema 的输入。
- 同一批次绑定一个应用和受理时的业务 Bundle。公共参数在提交前合并到每行，由服务端逐行复核。
- CSV、TSV 和从表格粘贴的数据预览、显式列映射、错误定位及逐行修正；结构化编辑和附件继续服从应用契约。
- 批次受理、持久输入、有限并发派发、准入背压、恢复、本人查询和管理面查询。
- 全部逐项状态、等待输入和审批摘要；补充资料、审批及单项取消复用原服务。
- 停止后续派发、取消未结束项、符合重做条件的失败项显式创建派生批次。
- 当前授权范围内的结果汇总和 CSV 导出，以及批次、输入文件、业务 Bundle、历史页面的保留规则。
- 扩展现有页面创作上下文、SDK、静态检查和隔离模拟检查，并完成真实 AI 页面与正式调用的系统验收。

首期不包括原生 XLSX 文件导入、通用数据表、跨应用混合批次、多轮会话批量编排、自动修改工作流、定时批次、新增 MCP 批次工具或业务页面批量批准。Excel 复制得到的 TSV 属于本期粘贴能力，不等于原生 XLSX 支持。

## 5 核心业务规则

1. 用户明确提交后，Runtime 先保存完整批次和逐行输入，再由后台派发。关闭页面或断线不停止已受理批次；受理前的表单不是后台任务。
2. 接收错误不部分开跑。任一输入不合法时返回批次和行字段错误，用户修正后重新提交；不得显示为已成功受理。
3. 每个项目有稳定行标识和原始顺序。重复内容可以表示不同业务项目，不以内容相同自动去重。
4. 重复请求使用原幂等键返回原结果；同键换数据返回冲突。刷新、网络错误或模型建议不能生成新的业务意图。
5. 一项等待资料或审批时，其他独立项目可以继续；仍遵守租户总在途、队列、模型、工具和沙箱配额。
6. 发布切换不改变已受理批次的输入、业务版本和原页面。撤权、停用和凭据撤销仍按正式 Admission 检查，不因批次冻结而获得永久授权。
7. 停止派发只停止尚未开始的项目；取消未结束项另外调用原取消服务，已完成外部操作不自动回滚。
8. 失败项重做由用户明确确认，创建绑定当前有效发布的新派生批次。原批次、原调用和结果保留；结果待核实或不可安全重放的副作用不自动重做。
9. 状态和进度来自权威调用数据，不依赖 Trace 到达顺序，不用计时器推算进度。失败、取消和待核实分别展示。
10. 不共享或伪造 Session。长期记忆继续使用既有用户作用域；独立 Invocation 不意味着外部系统、业务数据或用户记忆自动隔离。

## 6 既有能力与新增内容

| 能力 | 当前基线 | plan10 增量 |
| --- | --- | --- |
| AI 页面创作 | 同一工作 HTML、持续对话、预览、发布及历史 | 批量能力上下文、模拟批次和检查场景 |
| 页面 SDK | 单项调用、本人记录、查询/订阅、输入、取消、文件和审批跳转 | 批次提交/查询/打开、分页项目、派发控制和导出 |
| Invocation | 正式运行、幂等、权限、等待、审批与恢复 | 批次来源关联，复用正式受理服务 |
| Runtime | MySQL 权威、Outbox、Lease/Fencing、Redis 派发和准入 | 同一运行产物内的批次协调和恢复 |
| 管理界面 | 应用调用记录、执行记录、待审批 | 调用记录子页及批次下钻 |
| 文件 | Artifact 上传、归属、Hash 和保留 | 导入来源、未派发输入引用及汇总导出引用 |

页面检查器分别验证单项提交和批次提交；一次批量提交必须只创建一个模拟批次及准确 N 项，并拒绝漏行、重复提交和循环调用 `invoke`。隔离检查不产生正式 Invocation，仍须通过真实模型与正式业务验收。

## 7 架构变化

plan9 首期明确不建设通用批次对象。plan10 在 Runtime 增加面向同一应用的持久批次协调，以解决未派发项目在关页后丢失、重复提交、版本混用和跨任务汇总问题。

变化不新增部署产物、工作流 DSL 或跨面数据库访问。Control 保留创作和管理入口，管理查询经 Runtime 内部接口及现有授权执行；Runtime 管理批次、单项受理和恢复；Observability 继续记录 Trace 与成本，不决定业务状态。详细协议和边界见 [设计方案](design.md)。

## 9 完成定义

- 契约、初始化 DDL、Runtime、Control 管理接口、前端、SDK、页面检查和系统测试一并交付。
- [验收矩阵](acceptance.md) 的适用场景全部通过，真实生成页面可在正式发布后运行；不以固定手写 Demo 代替。
- 受理、派发与调用之间的强退窗口、发布切换、撤权、历史恢复和文件归属有可复现证据。
- 不保留旧语义包装、猜测式字段转换或浏览器队列 fallback；历史发布物按既有引用和 Retention 规则保留。
- 复用现有依赖和自动化；新增仓库编排只使用 Python，前后端单文件不超过 2000 行。
- 原始失败、专项复测、预算和证据分别记录；临时资源清理并恢复开发副本。plan7/planv2 的未关闭生产认证不随本计划自动完成。
