## 原始失败与修复

1. `system-01`：本机默认 Helm 4 与现有工具调用不匹配。后续显式使用已有 Helm 3。
2. `system-02`：本机 Docker OpenSandbox 不支持 secureAccess。测试 Values 使用现有受支持的本地连接方式。
3. `system-03`：测试模型 CA 滚动更新期间，旧 Gateway Pod 的端口转发返回 draining。测试准备等待旧 Pod 退出及新入口就绪。
4. `system-04`：MySQL 二进制排序的行 ID 被驱动视为字节串；已改为无损 UTF-8 解码。
5. `system-05`：4 项通过后，恢复测试批次停在 queued。后台剩余项目 COUNT 被错误解码为无符号类型，派发事务回滚；候选 07 使用数据库实际有符号类型，并准备重新执行全部受影响系统门禁。

构建前复核还修复了共享取消服务的对象查询参数遗漏，取消命令和事件明确记录真实操作人；新增管理员取消他人 API 批次的系统断言。还补齐批次查询、单项投影及导出冻结的事务级一致性快照，Runtime 原写入隔离级别保持不变。架构边界检查通过，无新增例外。

6. `system-06`：一致性快照与 C01 通过，但 C02 并发回放遇到 `INSERT IGNORE` 共享锁升级死锁；后台另发现保存点不能通过预处理语句协议执行。候选 08 使用立即取得排他锁的无变更 Upsert，并从原子项目存在性识别回放；保存点使用 SQLx 原生文本命令；首次编译发现 `raw_sql` 异步生命周期限制，改为原生 `Executor::execute` 后严格检查通过，原始编译诊断保留。并发测试扩大为 5 轮、每轮 4 请求，仍要求全部正常返回同一批次。

7. `system-07`：9 项通过、3 项失败。强退测试的暂停点识别及根数据库客户端字符集属于测试问题，均已修正且不降低强退/关联/授权断言。实际导出因 S3 客户端未启用条件写而返回 NotImplemented；候选 09 显式启用成熟库的 ETag 条件写，导出测试还增加文件写成、元数据提交前强退及原文件恢复校验。现场诊断后使用原部署工具清理临时环境。
