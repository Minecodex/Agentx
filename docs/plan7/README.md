# plan7：产品最后一公里与生产收口实施计划

plan7 覆盖五个经过 n8n 与 Dify 源码对比研究后选定的最高投入产出比事项。研究结论（2026-09，基于三方源码通读）：

1. Agentx 的执行内核、可靠性与治理（Checkpoint-Fork、审批会签、lease/fencing、配额审计）已达到或超过 n8n/Dify 同类实现；
2. 差距集中在产品最后一公里（IM 出站回复、LLM 流式、终端用户体验）与生产认证收口；
3. 生态差距（连接器数量、插件市场）不通过追赶解决，由既有 MCP + 画布插件路线承接，不在本计划内。
4. 2026-09-26 完成五线全量源码勘察：各线"现状事实"已逐项核实并修正（修正内容以"勘察修正/勘察新增/勘察利好"标注直接并入各线正文），关键实现设计与先决决策见各线文档与本文 §2。


其余各线互不依赖，可并行。

## 3. 全局约束

沿用仓库现行规则，本计划所有任务必须遵守：

1. 前后端单文件不超过 2000 行；新模块按关注点拆分。
2. 不保留向后兼容：过时表、DTO、API 直接删除，不写迁移层和 fallback（项目处于开发期）。
3. 跨平台自动化只写 Python；Kubernetes 系统级 E2E 以 `pytest tests/e2e` 为唯一编排入口，浏览器操作走 `tests/browser` Playwright；测试用临时 Namespace，结束后删除并恢复被缩容的开发服务。
4. 契约先行：改 `contracts/openapi` 后必须重新生成 `src/web/src/shared/api/generated.ts`；协议/Schema 冻结以契约测试为准。
5. 本地证据统一写 `.local/artifacts/e2e/<run_id>/`，证据不得包含 Secret、Token、完整请求体。
6. 每条线完成时：契约测试、静态边界检查（`cargo xtask check`）、Rust 单测、前端 vitest、Kubernetes E2E 全绿后才允许勾选任务与更新本文档状态。

## 7. 桌面端手动界面验收流程

本地入口为 `https://agentx.localhost`，Runtime 入口为 `https://run.agentx.localhost`。使用现有管理员账号登录，测试数据统一以 `P7-手测-日期` 命名。先准备资源，再按下面的顺序操作；每次记录版本、执行 ID、页面截图和结果。语言/主题检查使用桌面浏览器，不包含移动端。

### 7.1 准备资源与两个工作流版本

1. 在“凭证”创建测试模型与知识库所需凭证，在“模型”接入可用模型并测试连接。准备一个支持流式文本的模型；多模态测试另需支持图片的模型。模型能力与计价按真实服务填写。
2. 在“知识库”接入真实 LightRAG 或 RAGFlow，确认连接健康。LightRAG 外部资源 ID/workspace 只能使用 1–128 位 ASCII 字母、数字、下划线；RAGFlow 使用实际 dataset ID。本地核心安装不自动部署这两个知识服务，也不自动配置模型或 IM 凭证。
3. 新建工作流，定义字符串输入 `question` 与字符串输出 `answer`。使用“开始 → 模型/Agent → 结束”，通过界面的变量选择器绑定输入、模型输出和结束输出，先完成一次画布调试。多模态版本另需声明文件/附件输入，并在模型节点将其绑定为相应多模态输入。
4. 为工作流授予模型、所用凭证、知识库等实际使用资源的权限。发布 V1（简短回答），修改为详细回答后发布 V2；确认两个版本都能单独执行。
5. 新建应用并发布到其中一个版本，在“会话体验”选择应用。点击右上角“参数映射”，将问题输入映射到 `question`，回答输出映射到 `answer`；多模态版本还需映射文件输入。等待映射发布为生效状态，再新建会话发送消息。后续修改版本后要重新发布应用并检查映射，评测则直接选择对应的不可变工作流版本。

### 7.2 P7-B：流式、多模态与 Studio

| 操作 | 预期结果 |
|---|---|
| 会话体验发送一个需要分段回答的问题 | 回答逐步出现，终态内容与执行输出一致；执行记录有状态、耗时和 token 信息 |
| 输出中点击停止，或刷新后重新打开同一会话 | 停止请求有明确状态；已持久化消息可恢复，不把未完成回答显示为成功 |
| 上传 PNG/JPEG 并询问图片内容 | 支持图片的模型能回答图片内容；附件、请求和最终消息正确关联 |
| 使用不支持该附件类型的模型/配置执行 | 显示明确能力或输入错误，执行失败原因可查 |
| 在画布中执行模型节点，打开运行面板/节点详情 | 运行时可见文本增量；结束后显示正式节点输出；支持 reasoning 的模型可见对应内容 |
| 从执行记录打开 Trace、模型调用详情 | 节点/Attempt/调用层级、输入输出、错误和 usage 可查看；观测延迟时显示延迟状态，稍后可补齐 |

音频和文件需要相应模型协议与能力支持，再按同样流程测试；图片通过不代表所有多模态类型都已通过。未配置价格时成本可为 0，不能以此单独判为失败。

### 7.3 P7-E：文档管理与检索

1. 打开 LightRAG 资源详情的“文档管理”，上传 UTF-8 `.txt`/`.md`。内容可用：`P7 手测项目的发布代号是 sapphire-orbit-20261008。`
2. 等待文档行从“上传中/索引中”变为“已索引”；上传受理不能当作索引成功。确认最终外部文档 ID、索引时间可查。
3. 在“检索测试”询问发布代号，确认真实分段包含上传内容，并显示来源信息；外部服务未提供分数时允许为空。
4. 再传相同内容，检查重复拒绝；上传不支持类型和超限文件，检查前置错误。索引中尝试删除应被拒绝。
5. 将该资源授权给 Agent 工作流，调试 `knowledge_search`，确认运行时能命中管理面上传的同一内容，并查看 Trace 引用。
6. 删除已经终态的测试文档，确认平台列表/原件引用更新，并注意确认框说明：外部索引仍需在外部服务清理。
7. RAGFlow 资源应显示“外部自管”说明；对预置 dataset 执行检索测试。其文档上传在 RAGFlow 侧完成。

### 7.4 P7-C：评测、比较与运行洞察

1. 在“测试集”添加至少 3 条用例，输入对应工作流的 `question`，期望输出对应 `answer`，使用稳定且不同的 case key，发布测试集版本。
2. 在“评测报告 → 评测方案 → 新建评测方案”添加包含文本等基础规则，再添加“LLM Judge”，选择已授权的评估模型。提示词引用 `{{actualOutput}}` 与 `{{expectedOutput}}`，要求仅返回 `passed` 布尔值、0–1 的 `score`、字符串 `reason`。
3. 使用相同测试集和方案分别评测 V1、V2。等待完成，检查逐用例输出、规则通过/失败、Judge 理由/分数、耗时和成本，点击“评测 Trace”应进入真实评估子执行。
4. 选择 2–5 次运行进行“对比”，第一项作为基线。确认按 case/rule key 对齐，指标差值和费用/耗时变化正确；再用包含新增/缺失 case key 的测试集版本跑一次，检查“缺失”显示。
5. 使用未授权的评估模型，确认不能正常启动并显示授权错误；恢复授权后重新发起评测。
6. 在“运行洞察”按工作流和时间筛选，检查调用量/成功率、成本趋势、错误 Top、节点耗时。先产生成功调用和一个专用测试版本的可控失败，再点击错误分布，确认进入执行列表且错误码过滤保留。

### 7.5 P7-A：渠道入站、出站与投递记录

1. 应用详情新建钉钉/飞书/企微渠道，填写真实平台配置。确认必填输入已预先列出且来源为空，输入下拉框包含全部必填和可选输入；配置必填来源，按需添加可选映射或固定输入。首次应用部署前也应能使用最新工作流版本的字段。将“开启回复”设为“开启”，确认此时才展示“回复输出字段”下拉框与“回复模板”多行文本框；选择输出字段 `answer`，填写含 `{{output.answer}}` 的多行模板。关闭再开启应保留未保存的内容，保存并重新编辑应完整回显。配置保存后发布应用，使渠道修订生效。
2. 钉钉 Stream、飞书长连接可先测试；HTTP 回调及企微要求平台能访问 Runtime 的公网 HTTPS 回调地址，本机 `localhost` 地址不能直接用于平台回调。
3. 在对应平台向机器人发送文本，确认产生执行并收到 `answer` 回复；再测试私聊/群聊，确认回复到原会话。
4. 应用详情“投递记录”检查待投递/投递中/已投递状态、次数、平台消息 ID；重复入站事件应只有一次业务处理和回复。
5. 用专用测试配置制造平台认证失败或限流，确认可见错误和重试次数。达到死信后恢复配置，点击“重放投递”，确认成功且未重复生成业务执行。
6. 使用显式回复/发送消息节点和 Loop 分别测试：同一节点激活重试幂等，不同循环激活应各自投递。关闭“开启回复”并重新发布应用后，确认自动结果回复关闭，显式节点行为仍遵循工作流配置。

### 7.6 P7-D1：知识、记忆与沙箱联调

1. 在“记忆”接入真实 Mem0 并测试连接，在“沙箱配置”准备可用 OpenSandbox 配置和已批准的镜像摘要。分别授权工作流所需的凭证、记忆与沙箱资源；本地核心安装不自动部署 Mem0。
2. 在一个专用工作流中组合“开始 → Agent → 代码 → 结束”。Agent 绑定模型、知识库和长期记忆；代码节点选择 Python 与沙箱配置，执行返回输入内容的简单函数。调试成功后，在节点输出和 Trace 中确认知识检索及沙箱执行确实成功。
3. 将 Agent 会话策略配置为应用会话，发布工作流和应用。在同一用户、同一应用的“会话体验”里明确要求 Agent 将一个独特信息写入长期记忆；再新建会话要求召回。除了回答内容，还要确认 Trace 中有成功的记忆写入与召回调用，避免把聊天上下文当成长期记忆。
4. 使用另一用户或应用验证记忆作用域隔离。画布调试没有可信应用会话主体，长期记忆调用应明确拒绝；这条拒绝路径与应用会话的成功路径分别记录。

### 7.7 权限、UI 一致性与 P7-D 边界

用另一个部门的用户检查知识资源、检索、评测报告和运行洞察范围；再检查资源授权的申请、批准、拒绝、过期、撤销等状态。对比管理员与普通用户的入口及错误提示，不能仅靠隐藏按钮阻止越权。检查中文/英文、浅色/深色主题、空态、加载态和错误态，记录浏览器控制台或网络请求中的异常。

“Runtime 状态”页面可检查服务健康、执行收敛和恢复状态，手动流程可验证发布、执行、Trace 闭环。P7-D 的两小时容量、数据库恢复、滚动版本混跑、镜像签名和九域发布认证必须使用既有自动化与运维入口；界面测试通过不能替代这些门禁。
